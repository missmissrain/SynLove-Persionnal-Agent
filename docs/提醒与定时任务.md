# 提醒与定时任务（v1.3.3）

提醒这条线换过一次实现，原因很直接：**会话内定时不可靠**。

## 为什么不用会话内 schedule

早期用 Harness 的 `schedule` 插件：到点往"同一会话"塞一条 follow-up，再走 outbox 发微信。
问题有三：

1. 会话必须活着、且 agent loop 在跑，才会处理这条 follow-up；
2. 微信发送窗口只有 **5 分钟**，到点时你八成没在聊天，消息只能"停放"等你下次说话；
3. 链路重启一次，定时器就丢了。

于是改成**独立进程 + 直推通道**。

## 现在的结构

```
reminders/reminderService.py     常驻，每 30 秒扫一次 SQLite
        │  到点 → 直接调 QQ 主动推送（不经过会话、不经过 outbox）
        ▼
runtime/reminders.db             表 reminders(id, text, rule, next_at, ...)
        ▲
        │  增删查
reminders/mcp/reminderMcp.py     给模型的三个工具（stdio MCP）
```

| 工具 | 作用 |
|---|---|
| `remind_add` | 建提醒：一次性（`after_minutes` / `at`）或每天（`daily_at`） |
| `remind_list` | 列当前所有未完成提醒 |
| `remind_delete` | 按 id 删除 |

到点后写 `runtime/reminder-service.log`，并把提醒标记为已触发（每天型自动算下一次）。

## 为什么默认走 QQ

| 通道 | 主动推送 | 结论 |
|---|---|---|
| 微信 iLink | 只在"用户刚发过消息"的 5 分钟窗口内可发 | 不能用来做定时 |
| QQ 官方机器人 | 主动消息有配额，但**随时可发** | 提醒默认走这里 |

所以"每天 12:00 该吃药了"这类需求，回复里会明确说是推 QQ；微信只负责你正在聊时的即时回复。

## 启动与自愈

- `start_stack.py` 调 `ensure_reminder_service()`：`runtime/reminder.pid` 活着就跳过，否则后台拉起；
- 进程崩了不影响对话，最坏是这一轮提醒晚几分钟；
- 改完提醒规则不需要重启服务（每轮都从库里读）。

## 新闻日报也是这条路

每天 **08:55** 的新闻摘要用同一套思路：计划任务 `SynLoveNewsDigest` 触发
`newsDigest/runDigest.py`，采集 → 去重 → 本机 Gemma 筛选改写 → **QQ 直推**。
数据源见 `docs/音乐与歌单.md` 之外的那份说明，重点是：新闻走本机 RSSHub 与官方公开 API，
不再用浏览器抓页面（没有验证码，也没有登录态问题）。

## 边界

- 没有 cron 表达式，只有"一次性 / 每天 HH:MM"；"每周五"要靠每天任务里自己判断或改代码；
- QQ 网关断开期间平台**不补发**，那一条就丢了（日志里能看到）；
- 提醒正文建议短句，QQ 主动消息有条数限制。
