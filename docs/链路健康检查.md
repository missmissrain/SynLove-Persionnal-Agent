# 链路健康检查与自愈（2026-10-30 复盘）

> 这篇是为了回答一个问题：**人在外面的时候，微信/QQ 会不会悄悄失活？**
> 结论是：原来会，现在把最大的那个盲点补上了。

## 1. 那次「看起来活着其实没用」的事故

时间：2026-10-30 09:00（当地时间；探针日志里是 UTC 01:00）。

现象：用户发 QQ 消息，欣爱回「我这边刚才没处理成，稍后再试一次好吗？」。

排查结果：

```
qq.gateway  已连接 / READY        ← 网关是好的
pid 文件    进程活着              ← 进程是好的
qq.handle_failed                 ← 但每一条消息都失败
  RemoteError: agent-presets: preset "weixin-lite" failed to mount:
  1 row(s) did not activate:
  skill (@deepseek-ai/dsh-skill): service "skills" has been registered
```

**所有基于「进程在不在 / 端口通不通」的巡检都会放过这个状态。** 网关连着、进程活着、
端口都在，唯一的问题是新建会话时 preset 挂不上，于是每条消息都走异常分支。

根因：`weixin-lite` preset 里的 `skill` 三行是裸挂载，而 `skills` 是宿主已注册的服务
（和 `compaction` 一样），重复注册 → 整个 preset 挂载失败。
修法：把三个 skill 插件包进 `cordis:group` + `isolate: { skills: true }`，
建私有实例。preset 文件在 `~/.dsh/.agent-presets/weixin-lite/agent.cordis.yml`，
本仓库 `config/agentPresets/` 留了一份参照副本。

## 2. 现在每一层都有检查

| 层次 | 检查什么 | 谁在做 | 失效时怎么办 |
| --- | --- | --- | --- |
| 进程 | harness / console / Gemma / RSSHub 端口是否在听 | `start_stack.py` + 计划任务 | 重新拉起 |
| 进程 | 巡检自己的 pid 文件 | `SynLoveGuard` 计划任务（每 5 分钟） | 重新拉起巡检 |
| 协议·微信 | 探针日志里 `poll.*` 是否还在（静默 > 5 分钟） | `guardService.check_weixin_stall` | 重启整套栈 |
| 协议·微信 | 投递是否卡在非终态、outbox 是否卡住、租约是否属死进程 | `guardService` 每 60 秒 | 强制收尾 / 清租约 |
| 协议·QQ | 网关 pid 是否活着 | `guardService.check_qq_gateway` | 重启整套栈 |
| **语义** | **能不能建会话（从真实流量推断，不制造假会话）** | **`guardService._preset_evidence`（每 60 秒）** | **心跳标红 → 进自愈** |
| **语义** | **本地 Gemma `/health` 是否应答** | **同上（每 60 秒）** | **连续 2 次失败 → 重启整套栈** |
| **出站对账** | **收到了却没发出去 / 推送被平台拒绝** | **`guardService.check_outbound_health`（每 60 秒）** | **通过 QQ 通道告警（1 小时去重）** |
| **入站对账** | **消息收到了但没处理成（哪条、为什么）** | **`guardService.check_inbound_failures`（每 60 秒）** | **通过 QQ 通道告警（按 delivery_id 去重）** |
| 任务 | 技能复盘 03:00 是否跑成功 | `guardService.check_skill_review` | 补跑 |

## 2.2 入站能不能抓出来：分清「到了没成」和「压根没到」

| 情况 | 能不能抓 | 依据 |
| --- | --- | --- |
| 消息到了、但没处理成 | **能，100% 有记录** | `delivery.status = failed_terminal` + `last_error`；QQ 侧是 `qq.handle_failed` |
| 消息压根没到本地 | **不能直接抓** | 平台不给对账接口：QQ 的 at 事件是推送式，断线不补发；微信是长轮询，本地看不到平台侧有没有积压 |
| 没到的间接判断 | **能推断窗口** | 网关异常断开、长轮询停摆的时间段 = 可能漏消息的时段 |

真实失败样本（`delivery.last_error`）：

```
stuck in control_applied (manual recover 2026-10-28 20:34:27)   11 次
stuck before terminal (guard recover)                            1 次
stuck in routing (manual recover 2026-10-28 20:34:27)            1 次
用户已取消，之后不再自动重投                                       1 次
```

随时可查的审计工具：

```bat
python tools\inboundAudit.py --hours 24 --probe
```

输出「收到几条 / 成功几条 / 失败原因 / 链路断过多久」，并且会把
**正常保活重连（op=7，平台每小时要求一次）**和**异常断开**分开计数——
不分开的话一天 24 次正常重连会把真正的异常淹没。


语义层那一行已经改过两次，最终形态是**纯被动观察**：

> **不要为了探活去造一个假会话。** 第一版用 `POST /admin/reload-preset` 每 10 分钟
> 真建一个探针 Agent 再释放——这个接口本身没问题，但**定时调用等于每 10 分钟和欣爱
> 建一次会话**：污染会话列表、可能撞上正在进行的对话、纯属浪费。已移除。
>
> 现在改成从既有证据推断，零副作用：
> - 正常证据：探针日志里的 `agent.created` / `agent.resumed`，或 `delivery` 里
>   最近一条 `status=injected`（消息成功交给模型 = 会话建起来了）；
> - 故障证据：`qq.handle_failed`、`preset.reload_failed`、`admin.failed`；
> - 两边比时间戳：故障更晚 → **异常**；正常证据在 6 小时内 → **正常**；
>   两样都没有 → **未验证**（如实说不知道，绝不假绿）。
>
> 代价是「长时间没人发消息」时无法主动证明能建会话——这是可接受的：
> 没有流量时确实没有证据，硬造流量才是问题。

## 2.1 出站心跳：系统本来就知道推送成没成

不用主动发测试消息，状态库里已经记着每一笔进出（`~/.dsh/weixin-state.db`）：

| 表 | 字段 | 含义 |
| --- | --- | --- |
| `delivery` | `status` / `last_error` / `injected_at` | 收到的消息有没有成功交给模型 |
| `outbox` | `status` / `last_error` / `sent_at` | 要发的消息：`sent` 还是 `failed_terminal` |

真实样本（2026-09 的失败记录）：

```
status      failed_terminal
last_error  会话窗口已关闭，通知不补发（按配置即丢）
```

这就是「主动推送失败」最典型的形态：微信的会话窗口关了，平台直接拒收，
原因明明白白写在 `last_error` 里。QQ 那边等价的信息在探针日志里：
`outbound/qq.send {session_id, mode, ok, error}`。

于是 `check_outbound_health` 做两件不需要打扰你的事：

1. **收得到发不出**：最近 30 分钟有入站、却零条出站 → 说明"你发了消息她不理"；
2. **推送被平台拒**：最近 2 小时 `failed_terminal` 按原因聚合，同类 ≥3 次 →
   用**另一条通道**（QQ）把原因告诉你，两条链路互为备份。

告警 1 小时去重，不会刷屏。

## 3. 顺手修掉的一个假检查

`check_weixin_stall` 原来有个静默失效的问题：

```python
lines = probe.read_text(...).splitlines()[-80:]   # 只看最后 80 行
...
if str(item.get("event", "")).startswith("poll."):
    has_poll = True
...
if has_poll and last_at > 0 and time.time() - last_at > 300:
```

只要 QQ 的事件把 poll 挤出最后 80 行，`has_poll` 就是 False，
**整条检查直接跳过**——微信真卡死了也没人管。现在改成扫最近 800 条，
并且只在「窗口里出现过 poll」时才用时间戳判断（避免刚启动还没开始轮询就误杀）。

## 3. 自动自愈：失败 → 重启+清状态 → 验证 → 停机

前面几节都是「发现 + 告警」，这一节是「动手」。实现在 `tools/linkSupervisor.py`，
由巡检每分钟调一次 `tick()`。

```
发现新失败（入站 failed_terminal / 出站 failed_terminal / preset 挂不上）
      ↓
第 1 次自动恢复：L0 重启栈 → L1 清死锁 → L2 清状态库 → 验证 preset
      ↓
  ❌ 还是不通 → **交给编码 agent 自修**（见 3.1）
      ↓
再次恢复 + 验证 preset
      ↓
用 QQ 推送一句"请重发刚才那条"        ← 推得通 = 回传通路真的回来了
      ↓
  ✅ 成功 → 计数清零，阶段 recovered
  ❌ 失败 → 计数 +1，阶段 retrying，10 分钟后（冷却）再试一次
      ↓ 第 2 次仍然失败
  🛑 停机：停掉整套栈 + 写 guardian.pause（24 小时）→ 不再空转
```

几个关键设计：

| 点 | 为什么 |
| --- | --- |
| 状态落盘 `runtime/link-supervisor.json` | 巡检进程重启也不丢「连续失败几次」，否则重启一次计数就清零，永远停不下来 |
| 10 分钟冷却 | 防止重启风暴：一次失败就狂重启，比故障本身更糟 |
| 双条件判定（恢复成功 **且** 推送成功） | 只恢复不推送，可能只是进程起来了；只推送不恢复，可能只是推送 API 通着 |
| 停机写 `guardian.pause` | 否则巡检的进程级检查会把它立刻拉起来，「停了又被拉起」死循环。现在 `restart_stack` 会先看这个标记，过期前一律不动手 |
| 30 分钟一条心跳 | 日志里看到「心跳：链路正常」说明状态机活着；看不到就知道巡检自己死了 |

停机后会再尝试推最后一条消息说明原因，然后彻底安静——等人工介入。

## 3.1 自修：重启治不好的故障交给编码 agent

2026-10-30 那次是 preset 里 `skills` 服务重复注册。这种故障**重启一百次也没用**，
L0~L3 全部无效，以前的结果就是「第二次恢复失败 → 停机」。

现在第 1 次恢复失败后会插入一步自修（`tools/codeRepair.py`）：

```
codex exec（主）→ 失败/没改动 → opencode run（备）
      ↓
只允许改：tools/、config/、~/.dsh/.agent-presets/weixin-lite/
      ↓
改完静态验证：Python 语法 + YAML 能否解析
      ↓
  ✅ 通过 → 重跑一遍恢复（reload-preset 才是真正的动态验证）
  ❌ 不通过 → 用自修前的快照整体回滚 → 走原来的停机逻辑
```

| 约束 | 值 | 为什么 |
| --- | --- | --- |
| 可改范围 | 三个目录白名单 | 提示词里写死，同时快照只备份这三个目录，回滚范围可控 |
| 禁止项 | 碰 runtime / secrets / 证书 / 删文件 / git / 装依赖 / 吞异常 | 自修最容易犯的错是"把检查注释掉让它通过" |
| 快照 | `runtime/coderepair-snapshot-<时间>/`，只留最近 3 份 | 项目不是 git 仓库，回滚只能靠快照 |
| 频率 | 冷却 30 分钟、每天最多 4 次 | 修不好就反复修会烧 token、改乱代码 |
| 超时 | codex 30 分钟 / opencode 8 分钟 | codex 高峰期实测很慢（小改也要几分钟），超时给足；opencode 一直很快 |
| 并发 | 后台线程跑，同一时间只允许一个 | 巡检照常每 60 秒一轮（心跳、Gemma 检查不停），但这期间不再启动新的恢复，避免两套动作打架 |
| 验证 | 静态（语法/YAML）+ 动态（recoverLinks 的 reload-preset） | 静态挡住"改出语法错"，动态才是"她真能起来" |

实测（假项目里放一个 `add` 写成减法的 bug，让它真去修）：

```
codex     59s / 22k tokens  → 改对，静态验证通过，自检通过
opencode  23s              → 改对，静态验证通过，自检通过
```

两个都测了一次真实的"改文件 → 验证 → 通过"。回滚路径也单独测过：
把改动改成语法错后，快照恢复原样、新增文件被删、密钥文件不受影响。

**为什么放后台跑**：codex 慢起来一次要十几分钟，如果同步跑，巡检会被占住，
那段时间心跳不写、Gemma 挂了没人管 —— 等于「为了修故障而让监控失明」。
现在自修在后台线程里跑，巡检照常每分钟一轮，只做一件事：这期间不启动第二次恢复。


## 4. 已知还覆盖不到的

| 情况 | 现在会怎样 |
| --- | --- |
| 出口网络断了（宽带上不了网） | 端口/`/health` 检查走本机，不会失败；但 QQ 网关会自己重连并打日志，微信 poll 会停 → 5 分钟后触发重启（重启也解决不了断网，但会留下日志） |
| 模型答得很慢但不报错 | 巡检认为健康；用户会感到慢 |
| 消息收到了但回复内容不对 | 巡检不管，属于质量问题不是链路问题 |
| 家庭宽带 IP 变了 / 断电 | 需要开机自启 + 计划任务，这套已经由 `install-autostart.ps1` 覆盖 |
| 半夜没人看 | 所有自愈动作都会写 `runtime/guard-service.log`，第二天可回查 |

## 5. 出门前 30 秒自检

```bat
:: 1) 四个端口都在听
netstat -ano -p tcp | findstr "3080 3081 3082 8080"

:: 2) 语义检查（能返回 ok:true 就说明 preset 挂得上）
curl -X POST http://127.0.0.1:3081/admin/reload-preset

:: 3) 巡检最近有没有报错
powershell -Command "Get-Content runtime\guard-service.log -Tail 20"
```

第 2 条最关键：**它过了，说明链路真的活着；它不过，发消息一定是「没处理成」。**
