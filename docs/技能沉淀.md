# 技能自动沉淀（v1.3.5）

管家每天做的事会重复："下载 B 站视频先要 cookie""酷狗取地址要传 `album_audio_id=0`"。
这些坑写在对话里会随上下文压缩消失，所以要**沉淀成技能文件**，下次直接加载。

## 一句话设计

**每天凌晨 3 点，用便宜的模型读前一天的对话 + 工具失败记录，把"值得复用的操作流程"写成固定格式的技能文件。**

```
skills/skillReviewService.py     常驻/计划任务入口（--once 跑一次）
skills/review/skillReviewer.py   复盘逻辑：挑素材 → 让模型写 → 校验格式 → 落盘
skills/review/llmClient.py       模型调用（qwen 主 / gemma 降级）
skills/review/reviewTools.py     只读工具：翻会话、查已有技能、看日志
skills/store/skillStore.py       落盘：新建技能 / 改已有技能进 .pending
skills/config/skillReview.json   开关、频率、模型、上限
```

技能库落在 `~/.dsh/skills/<name>/SKILL.md`，对话里由 `skill` 工具按需加载。

## 固定格式（不给模型自由发挥的空间）

```markdown
---
name: kugou-playlist-playback
description: 用酷狗 API 播放整个歌单时的正确顺序与坑
---

## 何时使用
...

## 步骤
1. ...

## 坑
- ...

## 验证
- ...
```

没有这四段就是格式不合格，直接丢弃重来。原因是：**只有"何时使用"才让模型能自己路由**，
只有"验证"才能让人事后确认这条技能真的可用。

## 模型怎么选

实测对比过：

| 模型 | 结果 |
|---|---|
| `qwen3.8-flash`（主） | 能写出可执行步骤，会保留具体的参数、命令、错误文案 |
| `gemma-4-E4B`（降级） | 酷狗素材只写出"先搜索然后播放"这种废话，没有可执行的细节 |

所以主模型是 qwen（便宜且够用），Gemma 只在云端不可用时兜底；降级时技能质量差，宁可少产出。

## 不重复、不打架

- **同一主题已有技能**：不让模型新建，而是产出"补充补丁"放进 `~/.dsh/skills/.pending/`，
  由人（或下次运行时）合并，避免两篇技能互相矛盾；
- **每轮最多 3 个新技能**（`maxSkillsPerRun`），否则一天能刷出十几篇没用的；
- **素材门槛**：至少 4 轮真实交互（`minTurns`），且必须包含"做成了/失败了"的明确结果；
- MCP 侧只给**读**能力（翻会话、列技能、看日志），**写权限不在模型手里**。

## 调度

| 任务 | 时间 | 入口 |
|---|---|---|
| `SynLoveSkillReview` | 每天 03:00 | `skills\runSkillReview.cmd` → `skillReviewService.py --once` |

跑完会在 `runtime/skill-review.log` 留一行结论（本轮看了多少素材、产出几篇、跳过原因），
有新技能时也会推一条 QQ 通知（`notifyQQ`），方便你决定要不要保留。

## 为什么是凌晨 3 点

- 不和聊天抢模型与显存（后面还有 Gemma 的摘要/图谱任务）；
- 素材是"昨天的"，凌晨正好凑齐一整天；
- 一天一次够了：技能是长期资产，频繁重写只会让它变味。

## 崩了会怎样：兜底、降级与复活

这一节是 2026-10-29 那次真实故障换来的：03:00 那一轮在写 `runtime/skill-review.log` 时撞上
文件被占用（启动脚本把 python 的 stdout 也重定向进了同一份日志，两个句柄写一个文件），
一个 `PermissionError` 冒到顶层，**整轮复盘直接崩、水位没推进、当天素材等于没复盘**。

四道补丁按"从里到外"排：

| 层次 | 做法 | 解决什么 |
|---|---|---|
| 写文件 | `skills/store/durableFile.py`：重试 6 次（退避到 2 秒）→ 仍失败就转存 `*.locked-<时间戳>-<pid>.bak`，**永不抛异常** | 杀软扫描、索引器、上一轮还没放开句柄 |
| 日志分流 | 启动器的 stdout 写 `*.console.log`，程序自己写的结论写主日志，**两者不是同一个文件** | 双句柄互锁（那次的直接原因） |
| 单实例 | `skills/store/runLock.py`：`O_CREAT\|O_EXCL` 抢锁，判活看"进程真在跑 + 启动时刻对得上 + 锁没过期" | 计划任务与兜底巡检并排跑、互相覆盖 |
| 复活 | `tools/guardService.py` 每 60 秒看水位：越过 03:00 十分钟宽限还没成功，就补跑一轮（30 分钟冷却） | 计划任务没起来、跑一半崩溃、进程被杀 |

两条"不丢素材"的规定：

- **模型失败不推进水位**。`skillReviewer` 报错时只写 `last_error` / `last_error_at`，
  `last_review_ts` 原地不动，下一轮（含补跑）会把这段素材重新覆盖一遍；
  否则一次 API 超时就等于永久丢掉一个窗口。
- **抢不到锁不算失败**。`--once` 撞上"已有一轮在跑"时返回 `ok=True` + `skipped=locked`，
  免得计划任务把正常情况记成失败、触发没必要的重试。

排障时看三个文件就够：

| 文件 | 看什么 |
|---|---|
| `runtime/skill-review.log` | 每轮结论（窗口、轮数、素材字数、新增/待审、错误） |
| `runtime/skill-review.console.log` | 进程崩溃时的 traceback（意外异常只在这里） |
| `runtime/guard-service.log` | 巡检有没有补跑、为什么补 |

一键手动补跑（不依赖计划任务）：`python skills\skillReviewService.py --once`；
想覆盖更长窗口：`--once --since-hours 30`（不推进水位时就是调试模式，加 `--dry-run` 则完全不落盘）。
